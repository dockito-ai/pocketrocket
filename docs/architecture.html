PocketRocket architecture

30 Oct 2026. How the app is put together: layers, modules, and the main flows. The why is in the BRD; the rules are in decisions.md, which wins over this page.

1. In one paragraph

PocketRocket is a fork of Termux with its own id, app.pocket. Termux supplies the Linux userland, terminal and foreground service. A separate Gradle module, :pocketrocket, holds everything of ours: native Compose screens and the code that drives command-line tools. Claude Code runs as the real CLI in stream-json mode, behind a chat UI. It is downloaded at first run and patched to use Termux's glibc loader. Git, gh and Dockito are driven through their own CLIs. Accounts are wired per folder through environment variables and git includeIf blocks. There is no server and no network of our own.

2. Layers

UI: Jetpack Compose, Material 3ui/: Rocket, Home (session grid), chat, workspaces, Git screens, the file manager, Settings, Health, Tools, Updates, setup. Built exactly as docs/ux-mockup/ (decision 23).

Upstream Termux files are touched as little as possible: TermuxApplication.onCreate() hands a few hooks to PocketRocket.kt, and TermuxService asks SessionKeepAlive whether it should stay up.

4. A chat session

Composer→Session→StreamJsonWriter→ stdin →claude -p→ stdout →StreamJsonParser→SessionReducer→SessionState→Compose
  • One long-lived claude -p --input-format stream-json --output-format stream-json --include-partial-messages --permission-prompt-tool stdio per session. It starts with an SDK-style initialize handshake. Permission asks arrive as can_use_tool control requests.
  • Model, mode, rewind (Edit/Retry) and interrupt are control requests on the same pipe. SessionReducer is pure: event plus state gives the next state. The fake transport replays recorded lines for tests and the demo.
  • The env comes from AccountWiring.envFor(folder): CLAUDE_CONFIG_DIR, GH_CONFIG_DIR, DOCKITO_ACCOUNT, plus POCKETROCKET_SESSION_FOLDER. Ordinary sessions (not Rocket's) get a short note about pocketrocket-workspace through --append-system-prompt.
  • SessionStore writes sessions.json on every change (temp file and rename). After a restart, sessions come back Paused. Opening one resumes it with --resume, and the conversation itself is read from Claude Code's own transcript.
  • Messages sent mid-turn wait in a Queued box until Claude reads them (decision 34). Attachments are copied to ~/.pocketrocket/attachments/; images and PDFs go inline, other files by path.

Control requests without a chat

McpPanel→ControlChannel→the session's process, or a short-lived claude -p→McpParser→McpPanelState→Status sheet, Connections
  • The probe has no way to send a user message, so no model call and no usage. It starts only on a button and always ends, by its caller or a watchdog. Replies to pr-config- ids skip SessionReducer, so the chat doesn't change.
  • mcp_status carries secrets in config. McpParser copies an allowlist, so they never reach the screen, the cache or a log. A request Claude Code doesn't know hides its action or falls back to the terminal.

Local MCP servers and plugins

Claude account screen→LocalMcpPanel, PluginPanel→AccountCli, per account's config dir→claude mcp add-json, remove, claude plugin … --json
  • The server list is read from the account's .claude.json without values; whether one works comes only from mcp_status, in a check started after each change. Edit is remove then add, and a refused add puts the old entry back.
  • Values typed on the phone go only into Claude Code's config and are never shown again. add-json has no stdin, so a server's values are on its command line while it runs; plugin options go on stdin. Parsers copy an allowlist, and output is scrubbed before it is shown.
  • Adding a server or installing a plugin shows the command or source first, since both run code on the phone. chrome-devtools stays with Tools, and synced plugins are read-only. One change at a time per account.

Skills, settings, output style and memory

Session's controls sheet, or Claude account screen→SetupPanel→the session's channel, or a probe→get_skills_dialog, get_settings, apply_flag_settings, update_settings
Claude account screen, or Workspace settings→MemoryPanel→MemoryFile→CLAUDE.md, temp file then rename
  • SettingsParser keeps only listed keys with plain values and a count of the rest, so env, hooks and helpers never reach the screen. Picks last for the session and are read back; saving is a separate button and only the two writes Claude Code allows. Managed values can't be changed.
  • A memory save compares a hash of the file with what was opened and writes nothing if it moved. Skill on/off isn't offered: its only route is a hidden CLI command.

Workspaces from a shell

pocketrocket-workspace→ <id>.req →WorkspaceRequests (FileObserver)→WorkspaceCliRunner→Workspaces.add, CloneManager→ <id>.out, <id>.exit →the script prints and exits

Requests go through ~/.pocketrocket/requests/, which only the app's uid can read. The app does the work with the same code as its screens, so the Workspaces list updates at once. Add, clone and list only (decision 73).

5. Staying alive and telling you

SessionManagerstatus change →SessionKeepAlive→TermuxService + wake lock
SessionManagerstatus change →SessionNotifier→"Needs you" / "Finished"
Question→Routercan't answer →AssistantBrain (hidden Claude session)MCP on 127.0.0.1 →AssistantToolsask_to_* →Approvals
Agent in AutoPreToolUse →AutoModeNeton the list: "ask" →a normal request, fingerprint
Rocket's Bash or MCP callPreToolUse /hook/rocket →AutoModeNet.decideForRocket"ask" →Approvals: fingerprint or yes

The service and wake lock are held only while some session is Starting, Working or waiting for permission. They are let go when every session is idle. Nothing starts on boot (decision 8). Notifications skip the session on screen, and the permission notification carries Deny, plus Allow when it shows the whole request, or Review when it doesn't. Allow needs an unlock, checked again in the receiver; the lock screen gets a private version.

6. Accounts, per folder

~/.pocketrocket/accounts/
  claude.json  github.json  dockito.json   lists and defaults, no secrets
  bindings.json                            folder → {claude, github, dockito}
  env.sh                                   same bindings for interactive shells (generated)
  claude/<id>/                             CLAUDE_CONFIG_DIR (first account is ~/.claude)
  github/<login>/gh/                       GH_CONFIG_DIR
  github/<login>/id_ed25519, gitconfig     key, identity, core.sshCommand
  dockito/                                 shared DOCKITO_CONFIG_DIR

bindings.json is the single source. ~/.gitconfig gets a managed block with an [includeIf "gitdir:<folder>/"] per bound folder. That way git from the app, from Claude or from a terminal uses the right key and author. The global gh auth switch is never used, because parallel sessions would fight over it (decision 21). Tokens stay in each tool's own config files.

7. First run and the relocated prefix

Termux bootstrapbyte-swap paths →pocketrocket-setup.sh→apt packages→Claude Code→Dockito→defaults
  • app.pocket is exactly as long as com.termux, so paths are swapped byte for byte. This happens in the bootstrap as it is extracted, and in every .deb through an apt DPkg::Pre-Install-Pkgs hook, after the signature check and before dpkg unpacks. Termux's mirrors are used as they are (decision 36).
  • Claude Code comes from downloads.claude.ai, checked against manifest.json (SHA-256). Its ELF interpreter is patched to glibc-runner, it is smoke tested, and it runs with autoUpdates: false. It is never bundled.
  • Dockito comes from its Homebrew tap release, checked against the formula's sha256, and goes through the same glibc launcher.
  • Optional tools install from Settings → Tools through the same script, never in the first run. Flutter & Rust (decision 75):
FlutterToolPage→FlutterRustToolScript →--only flutter-rust→FVM 4.3.2 (SHA-256)→tag clone, commit checked→Dart SDK→prepare glibc programs→rust from apt
flutter in a session→launcher: nearest .fvmrc or default→new Dart SDK? new engine tools?prepare →bash <version>/bin/flutter
fvm install / use / flutter→launcher as fvm: versions' scripts pointed, new ones prepared→FVM's own Dart→a version FVM cloned: Dart SDK, prepare, tool built
  • The setup script is also the updater's engine. --only claude, --switch X.Y.Z and --only dockito reuse the same download, check and smoke-test steps. Running sessions keep their binary until restarted.

9. Design rules

  • Drive the official CLIs and never reimplement them: Claude Code, git, gh, dockito, apt.
  • Each module has one concern and a small API. State is plain files under ~/.pocketrocket/ that a terminal or Claude can read too.
  • Termux changes stay minimal, so upstream merges stay possible.
  • Long work runs off the main thread and reports real progress (steps, bytes) to the screen.
  • Nothing secret is logged or copied. Conversations, codes and tokens stay where their tools put them.
